# CLAUDE.md

AI-бот підтримки для сервісного бізнесу: aiogram 3, Gemini через `ask_llm()`, база знань у YAML, передача адміну через групу з темами, SQLite, деплой на Railway. Один код — кілька ботів: кожен бізнес = свій YAML + свій `.env`.

## Як це влаштовано

- **Дані, а не код.** Усе про бізнес — у YAML: факти (ідуть моделі), а також службові розділи `prompt:` (роль і правила для моделі), `ui:` (тексти, меню, опис бота), `safety:` (медичний режим). Новий бізнес = новий YAML; правка коду під конкретний бізнес — сигнал, що бракує налаштування.
- **Промпт — прохання, код — гарантія.** Рішення «що бачить клієнт і чи потрібна людина» приймає `guards.resolve()`; невідкладний стан ловить `guards.pre_check()` ще до моделі. Фіксовані тексти передачі — `handoff.client_notice()`. Бот і eval викликають ці самі функції — тримай їх спільними.
- **Вибір бізнесу:** `BUSINESS_YAML` (вміст, для сервера) → `BUSINESS_FILE` (шлях) → `data/business.yaml`. `ENV_FILE` — файл налаштувань конкретного бота, читається перед спільним `.env`.
- **Дані реальних клієнтів — лише в `private/`** (у `.gitignore`): YAML, сценарії eval, звіти, `.env`. У публічних файлах (код, README, цей файл) — без назв і даних реальних клієнтів.
- Барбершоп (`data/business.yaml`) — публічне демо. Його промпт і схема відповіді мають лишатися незмінними, поки зміна не задумана навмисно: після правок у `prompts.py` / `llm.py` порівняй промпт до і після.

## Команди

```bash
source .venv/bin/activate
python -m bot.main                                   # барбершоп
ENV_FILE=private/<бізнес>/.env python -m bot.main    # інший бот
python -m bot.config                                 # перевірити налаштування

python -m unittest tests.test_guards -v              # гарантії коду, без моделі, ~1 с
uvx ruff check bot tests                             # лінтер (ruff не в requirements)
python -m tests.run_eval                             # eval барбершопу: 34×3 на живій моделі, ~9 хв
BUSINESS_FILE=private/<бізнес>/business.yaml \
  python -m tests.run_eval --cases private/<бізнес>/eval_cases.yaml
```

Eval перезаписує звіт поруч зі сценаріями (`tests/eval_report.md` відстежується git) — якщо прогін зірвався через API, поверни звіт: `git checkout -- tests/eval_report.md`.

## Як працювати з автором

- Спілкування українською. Коментарі й docstring у коді — українською, як уже в проєкті.
- Перед змінами — план; виконання після підтвердження.
- Після кожного кроку — пояснення логіки простими словами: автор пояснює це клієнтам.
- Деплой робить автор; агент лише описує, що налаштувати.
- Нові залежності — лише з поясненням, навіщо.
- Дані бізнесу — тільки з джерел, які дав автор; чого там немає або що суперечливе — не вигадувати, а винести автору списком.

## Git flow

- `main` завжди готовий до деплою: з нього деплоїться Railway.
- Кожна зміна — своя гілка `feat/<name>`, `fix/<name>` або `chore/<name>`, потім PR у `main`. CI немає, тож мерж — лише коли локальні перевірки (нижче) зелені.
- Коміти — Conventional Commits англійською: `feat:`, `fix:`, `docs:`, `test:`, `refactor:`, `chore:`.
- **Порадь, потім чекай.** Коли логічний шматок роботи готовий і перевірки зелені — запропонуй коміт (повідомлення + файли), пуш чи PR. Виконуй commit, push, створення PR і merge лише після того, як автор підтвердив саме цю дію.
- Перед «готово» — прогнати перевірки й показати результат як є, з провалами:
  - завжди: `python -m unittest tests.test_guards -v` і `uvx ruff check bot tests`;
  - якщо зачеплено промпт, `llm.py`, `guards.py`, `handoff.py` або YAML бізнесу — eval цього бізнесу (команди вище; потрібен робочий `GEMINI_API_KEY`).
